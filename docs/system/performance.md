# Алгоритмы, бюджеты и мониторинг

Это проектные решения и стартовые гипотезы на 2026-11-09. Замеров игрового runtime пока нет: SDK, сборка мода и тестовый мир не подготовлены. Числа ниже не являются характеристиками Satisfactory и не означают уже достигнутую скорость. При первом вертикальном срезе профильный reviewer пересчитывает оценки по коду, затем QA проверяет их измерением.

Связанные материалы: [план проверок](../testing/test_plan.md), [контекст проекта](../../PROJECT.md), [задачи](../../TASKS.md).

## Что ограничивается

Базовое поведение выполняется локально алгоритмами; GPU, Python, обучаемая модель и внешние сервисы ему не нужны. Не создавать поток на каждого бота. Unreal отвечает за движение, физику, столкновения и разрешённую игровую симуляцию; мод планирует намерения, не заменяет всё это собственным циклом.

Нельзя делать полное перечисление мира на каждом Tick или синхронно пересчитывать фабрику после каждого предмета в инвентаре. Основной путь — события, ограниченная очередь изменений и локальная инвалидация. Начальный scan и сверка после пропущенных событий остаются необходимыми O(W) операциями, но выполняются пакетами и имеют статус/прогресс. Переход от неполного снимка к полному не должен выдавать неизвестные значения за нули.

Работа с UObject и изменение мира выполняются на подходящем game thread/authority по контрактам движка. Фоновый solver получает неизменяемые данные без живых указателей на Actor, возвращает proposal с world/plan revision. Применение устаревшего результата блокируется на границе изменения мира.

## Размеры и оценки

Обозначения: W — обнаруживаемые мировые сущности; V/E — узлы/рёбра одного анализируемого графа; B — живые боты; Bw — воины с личными патрульными счётчиками; Q — все отслеживаемые незавершённые задачи, включая ready/blocked/active; R — активные резервы; C — просмотренные пространственные ячейки; K — кандидаты в локальном запросе; Kd — ограниченный пул кандидатов при назначении работы; D — замкнутый набор изменённых узлов **и рёбер**, включая все затронутые связи удаляемого узла; L — разрешённые попытки/глубина разложения; A — число хранимых кандидатов плана; S — размер одного неизменяемого снимка.

Оценки относятся к нашей структуре данных. Стоимость Unreal navigation, репликации, вызовов инвентаря, коллизий и сохранения измеряется отдельно. Наличие временного бюджета не позволяет прервать произвольный дорогой вызов движка посередине: адаптер обязан ограничивать размер вызова, а затем проверить worst-frame стоимость.

| Задача | Базовый выбор и предпосылки | Время | Дополнительная память | Альтернатива и компромисс |
| --- | --- | --- | --- | --- |
| Lookup EntityId/TaskId | Hash index с контролем размера | Ожидаемо O(1), worst O(n) при деградации hash | O(n) | Дерево O(log n) даёт более сильную worst-case гарантию; сравнить фактические контейнеры Unreal и distribution |
| Поиск локальных целей | Spatial hash/grid + проверка K кандидатов | Ожидаемо O(C+K); worst O(W) при скученности/большой области | Индекс O(W), запрос O(K) при материализации | Полный scan O(W) без индекса дешевле по памяти для очень маленького мира; spatial tree O(log W+K) при своих предпосылках |
| Выбор ближайшей допустимой цели | Однопроходный argmin по K с детерминированным tie-break | O(K) | O(1) сверх входа | Сортировка O(K log K) не нужна, если используется только один результат; top-k хранить ограниченной heap |
| Кратчайший путь в конечном графе | Dijkstra для неотрицательных весов; adjacency list и indexed binary heap с decrease-key | O((V+E) log V) | O(V) сверх входа | Lazy heap с повторными записями: O((V+E) log(V+E)), дополнительная память O(V+E), что существенно для multigraph; BFS O(V+E) допустим только для равных стоимостей; A* уменьшает практическую область при корректной heuristic, не гарантирует лучший worst-case |
| Посещение/старение узла патруля | Lazy decay от `stored_score`, `last_update`, текущего игрового времени; разреженная личная карта воина | O(1) на узел при вычислении score; выбор из K — O(K) | O(V) на одного воина, worst-case O(Bw × V) для всех личных карт; общий граф хранится отдельно | Сброс всех узлов O(V) по таймеру нарушает независимое старение; heap с динамически меняющимися ключами нельзя считать точным без корректной инвалидации. Общий счётчик посещений экономит память, но меняет поведение и требует отдельного решения |
| Очередь готовой работы | Фиксированное небольшое число классов приоритета, FIFO внутри класса, пространственный индекс; aging/fairness через события/квоты; динамическая цена пути и пригодность исполнителя оцениваются отдельно | O(1) enqueue/dequeue в FIFO; назначение одному боту дополнительно O(Kd) переоценок плюс стоимость маршрутов/запроса индекса; полный пересмотр B ботов — O(B × Kd) без стоимости путей | O(Q), индекс и scratch пула Kd | Heap O(log Q) подходит для статических deadline keys, но не заменяет dispatch. Статический heap не сохраняет точный порядок при изменении возраста, пути и исполнителя; ограниченный pool — сознательный приблизительный dispatch, не глобальный argmin по всем Q. Старейшие допустимые задачи входят в pool независимо от близости |
| Истечение lease | Indexed heap по expiry: ровно одна запись на активный lease + token/fence владельца | O(log R) на выдачу/истечение | O(R) | Lazy heap со stale-записями без compaction не ограничен активным R; такой вариант требует отдельного лимита bytes и O(R) перепостроения, распределённого по бюджету. Timing wheel имеет свои resolution/диапазон предпосылки, нужен только по замерам |
| Dedup запроса/команды | Hash по стабильному ключу эффекта, bounded active set и compacted завершённые операции | Ожидаемо O(1) lookup | O(активные + ограниченное окно replay) | Нельзя удалить idempotency запись раньше допустимого replay/checkpoint; бесконечный словарь создаёт утечку |
| Достижимость/затронутая область | BFS/DFS на dirty-подграфе с сохранением направления рёбер | O(Vc+Ec) | O(Vc) | Для лент directed reachability не равна слабой связности; питание обычно задаёт неориентированную топологию. Union-find не решает directed reachability и недостаточен для произвольных удалений |
| Циклы/сильные компоненты транспортного графа | Tarjan SCC для направленного графа | O(V+E) | O(V) сверх входа | Kosaraju также O(V+E), но построение reverse graph требует O(V+E) памяти, если обратные связи не были во входе. SCC объясняет топологию и не вычисляет throughput, max-flow или жидкостный напор |
| Начальный topology scan | Один проход по W + построение доступных рёбер | O(W+E) при O(1) разрешении ссылок | O(W+E) | O(W²) попарный поиск рёбер не допускается; размер одного batch ограничен |
| Порядок шагов плана | Топологическая сортировка DAG, проверка циклов | O(Vp+Ep) | O(Vp) сверх графа | Сортировка по числовому priority не заменяет зависимости и не доказывает допустимость частичного принятия |
| Анализ потока/производства | Поддержанные локальные модели, сначала наблюдаемые bottleneck и достижимость | Один структурный проход O(V+E); конкретный flow/solver имеет отдельную оценку | O(V+E) плюс scratch solver | Структурный проход не равен решению max-flow, fluid physics или глобальной оптимизации размещения; сложность каждого solver фиксируется перед его добавлением |
| Выбор улучшения фабрики | Ограниченное число A кандидатов и ограниченная область; hard constraints проверяются до оценки | O(A × F), где F — явная стоимость проверки/оценки кандидата | O(S + scratch + результаты A кандидатов) | Полный перебор размещений/маршрутов экспоненциален; ограниченный поиск предлагает лучший проверенный кандидат, не доказанный глобальный optimum |
| Граф на планшете | Delta updates + viewport/layer filtering; retained rendering | O(D) для полного набора node/edge изменений + стоимость видимой геометрии; удаление узла требует O(deg(v)) incident-edge работы; полный snapshot O(V+E) | O(видимая/кэшируемая часть) плюс обрабатываемые delta batches | O(D) не означает O(1) для команды «удалить высокостепенной узел». Полная копия/перерисовка всего графа на каждый кадр расходует CPU/GPU и сеть; при сложной карте нужен LOD и tile cache |

Заявление «алгоритмически» не означает бесплатно. Полное дерево всех будущих сценариев заранее не раскрывается: хранятся правила/операторы, небольшой текущий frontier и фактически открытые задачи. Каждая операция имеет лимит попыток, глубины и объёма результата. Пределы — часть контракта ошибки `BudgetExceeded/Blocked`, а не скрытое обрезание корректного результата.

Пиковая память считается целиком: resident index O(W+E), активные боты/задачи O(B+Q+R), личные посещения worst-case O(Bw × V), графы/снимки, результаты и nav cache с явным общим лимитом размера путей. Два параллельных solver могут держать две копии S. Предпочтительно разделять immutable snapshot с явным временем жизни; copy-on-write и двойной буфер тоже занимают память. TTL/LRU без лимита bytes не гарантирует верхней границы. Циклы физических транспортных графов допустимы; DAG требуется только для зависимостей исполнимого плана, а не для устройства фабрики.

## Планировщик и ограничение работы

Исполнение и анализ разнесены: solver не держит игровые locks, пока размышляет. Мир изменяется короткими проверенными операциями; конкретный готовый шаг не ожидает завершения анализа всей фабрики. Задачи маршрутов, сканирования, reconcile и анализа возвращают continuation, если исчерпан разрешённый объём.

Предлагаемая политика scheduler:

1. Обработка критических событий существующего действия: смерть, удаление цели, отмена и завершение уже совершённого эффекта.
2. Исполнение разрешённых коротких шагов и освобождение истёкших резервов.
3. Распределение ready-задач с квотами классов и bounded starvation; fairness проверяется на конечном потоке срочных заданий.
4. Фоновая аналитика, topology reconciliation и необязательная косметика в оставшемся бюджете.

Ранжирование не должно само стать бесконечным O(Q) циклом. Непригодный кандидат переводится в Blocked с причиной, retry time и версией наблюдаемого условия. Новый внешний факт будит его по индексу причин, а не полным перебором всех блокировок. Backoff ограничен сверху, отмена/смерть снимает leases, дедуп запросов не создаёт задачи «доставить запрос на доставку запроса».

При перегрузке сначала снижать частоту необязательного анализа/карты, объединять dirty-события и запрещать новый найм сверх принятого лимита. Не выключать урон, не дублировать содержимое сумок, не телепортировать ботов и не выполнять невидимую добычу ради FPS. Если работа действительно невозможна, безопасное ожидание с причиной полезнее бесконечного движения и фиктивного производства.

## Начальные профили нагрузки и гипотезы бюджетов

Профиль «первый срез»: 1 бот, два контейнера, короткий маршрут, карта закрыта. Профиль «обычная база»: 8 ботов, до 10 000 индексируемых сущностей, до 1 000 ready/blocked задач, одна аналитическая работа. Профиль «стресс»: 32 бота и увеличиваемая база/очередь до наблюдаемой saturation. Эти размеры — набор измерений, а не обещанный пользовательский максимум.

| Метрика | Предлагаемая отправная цель для обычного профиля | Как принимать |
| --- | --- | --- |
| Собственный scheduler/индексы мода на game thread | p95 ≤ 1 мс/кадр; отдельный собственный slice ≤ 0,25 мс | Trace timers по этапам; отдельно учитывать непрерываемые engine calls |
| Общий overhead кадра против того же мира без ботов | p95 ≤ 2 мс, p99 ≤ 4 мс | Одинаковые путь камеры/настройки, прогрев и несколько парных прогонов; отдельно native персонажи/анимация/навигация |
| Время до постановки ready-задачи в исполнение без нагрузки | p95 ≤ 250 мс | Интервал event accepted → assigned; без ожидания ресурсов/дороги/длинного игрового действия |
| Состояние UI после подтверждённого изменения | p95 ≤ 500 мс | Серверный ack → показ новой revision; недоставленная сеть помечается stale |
| Game-thread pause из-за solver | Ни одного синхронного ожидания полного анализа | Trace зависимостей и один искусственно медленный solver |
| Инкрементальная собственная память индексов/очередей/snapshot | ≤ 128 МиБ для заданного обычного профиля | Allocation tags; память мешей, UObject и навигации записывать отдельной строкой |
| Суммарная RAM/VRAM от мода | Фиксируется на первой сцене; числовой допуск согласуется по измерению | До появления ассетов/персонажа конкретная верхняя граница не доказана |
| История/диагностика обычного запуска | Кольцевой журнал; предложение лимита 64 МиБ, подробный trace выключен | Проверить реальный размер, ротацию и стоимость flush; активные финансовые операции нельзя вытеснять как debug-log |
| Внешний трафик, создаваемый модом | 0 запросов к внешним сервисам | Trace/socket/process accounting; игровые Steam/EOS соединения выделены отдельно |
| Сетевые дельты мода | Лимит измеряется по snapshot и steady-state; без передачи полного мира каждый кадр | Байты/с на клиента, peak late join, количество акторов и RPC; числовой лимит выбрать по первому прототипу |

Ни один новый лимит не удаляет уже существующих ботов/предметы. При смене профиля сверх текущего количества блокируется рост/откладывается необязательная работа; UI показывает последствия. Требуемая частота реакций на урон/коллизии обеспечивается механизмами игры, а не медленным опросом всей базы scheduler.

## Сбор измерений локально

Подтверждены официальные команды Unreal, но их доступность зависит от UE, build configuration и compile-time flags. Retail Satisfactory может не предоставлять все каналы/консоль. Сначала выполнить preflight и записать фактическую поддержку. Если команда недоступна, использовать совместимую development-инструментацию и явно указать ограничение; не рисовать нулевые показатели.

Для поддержанной сборки следующие **параметры запуска** добавляются к фактической команде тестового процесса, а не запускаются как самостоятельная shell-команда:

```text
-trace=cpu,frame,bookmark -tracefile=SAH_timing.utrace -notraceserver
```

Файл trace пишется локально. Не использовать `-tracehost`/`Trace.Send` для удалённого узла. Для короткой записи уже запущенной поддержанной сборки доступны команды консоли:

```text
Trace.Status
Trace.File SAH_timing.utrace cpu,frame,bookmark
Trace.Stop
```

Для Memory Insights канал включается **с начала процесса**; позднее подключение не заменяет недостающие allocation events:

```text
-trace=default,memory -tracefile=SAH_memory.utrace -notraceserver
```

`.utrace` открывается локальным Unreal Insights из совместимого engine toolchain. CPU scopes мода назвать по обязанностям: `SAH_Scheduler`, `SAH_Reserve`, `SAH_PathRequest`, `SAH_TopologyBatch`, `SAH_AnalyzeCandidate`, `SAH_CommitAction`, `SAH_TabletDelta`. Длительные job связывать BotId/TaskId/PlanRevision и counters: queue age/length, retries, blocked reasons, live reservations, graph nodes/edges, candidate count, stale proposals, bytes/cache. Реальные имена инструментирующих API фиксируются после проверки SDK.

`stat unit`, `stat gpu` и `stat RHI` пригодны для быстрой диагностики в поддержанной конфигурации. Они не заменяют raw trace и не гарантированно доступны в retail build. GPU/VRAM анализировать только на процессе с рендером; для dedicated GPU-метрики «неприменимы», не равны нулю. Накладные расходы профилирования измеряются отдельным коротким запуском.

Для локального Windows sampling без зависимости от языка названий perf counters можно использовать встроенные свойства процесса. Пример команды для 60 локальных отсчётов после подстановки проверенного PID:

```powershell
$sahProcessId = 12345 # PID тестового процесса из диспетчера задач
1..60 | ForEach-Object {
    $sahProcess = Get-Process -Id $sahProcessId -ErrorAction Stop
    [pscustomobject]@{
        TimeUtc = [DateTime]::UtcNow.ToString('o')
        Id = $sahProcess.Id
        CpuSeconds = $sahProcess.CPU
        WorkingSetBytes = $sahProcess.WorkingSet64
        PrivateBytes = $sahProcess.PrivateMemorySize64
        Handles = $sahProcess.HandleCount
        Threads = $sahProcess.Threads.Count
    }
    Start-Sleep -Seconds 1
} | Export-Csv -NoTypeInformation -Encoding UTF8 ./SAH_process.csv
```

Это штатная OS-команда для подготовленного Windows окружения; в текущем контейнере она не запускалась. CPU — накопленные секунды, для процента нужен delta CPU/delta wall time с явно указанной нормализацией на число ядер. Working set не равен всем аллокациям и не доказывает утечку. Peak из редкого sampling — максимум наблюдённых отсчётов, не гарантированный абсолютный пик. I/O/диск/сеть собирать доступными file/net trace каналами и OS counters, GPU — совместимыми средствами драйвера/движка; отсутствие доступа записывать как «не измерено».

## Воспроизводимое сравнение и утечки

Для каждого профиля зафиксировать сохранение и настройки, отключить debug-спам, прогреть одинаковый путь камеры, затем сделать минимум три сопоставимых коротких прогона. Предложение исходного интервала: 2 минуты прогрева и 5 минут записи. Это локальный тестовый бюджет; более долгая нагрузка на общий сервер требует отдельного согласования. Не сравнивать один загруженный первый кадр с прогретым baseline.

В отчёте хранить p50/p95/p99 и worst frame, число observations, время стадий, CPU-seconds, RAM/VRAM, allocations и освобождения, графы, активные/заблокированные задачи, I/O, байты сети и длительность. Сравнивать пары без мода → мод без ботов → мод с ботами, иначе нельзя отделить постоянную стоимость UI/индексов от native движения. Median/p95 агрегатов разных запусков не подменяет распределение кадров; сохранять исходные данные.

Сценарий утечек: прогрев → снимок A → одинаковые циклы найма/работы/смерти/удаления/загрузки → ожидаемая очистка и стабилизация → снимок B → повтор → снимок C. Начать с 10 циклов для проверки сценария, затем 100 при принятом лимите времени. Сравнить живые allocations по владельцу, Actor/UObject counts, delegates/timers, pending jobs, handles, потоки, GPU resources и сохранённые ссылки. Разрешённый cache должен выйти на ограниченное плато; постоянный рост неизвестного владельца — кандидат в дефект. Один большой RSS или ожидание GC сами по себе не доказывают утечку. Не применять принудительную GC каждый кадр ради «прохождения» теста.

Хранение подробных trace имеет срок/лимит и ручное включение; по умолчанию только короткие агрегаты и диагностируемые ошибки. Не записывать токены, пользовательские пути/имена аккаунтов и весь мир в каждый log-event. Корреляционные ID мода достаточны для восстановления сценария.

## Учёт затрат и приёмка

Для локального запуска нет выдуманного тарифа: записывать CPU-seconds, RAM/VRAM peak, GiB-seconds при наличии измерений, I/O bytes, network bytes и занятое место trace. По проекту внешние inference/API вызовы отсутствуют; это требование проверяется, а не доказывается нулём в отчёте. Денежную стоимость электричества можно вычислить только при измеренной энергии и заданном тарифе; без них писать «не рассчитано».

Независимый reviewer проверяет: нет скрытых копий S, отложенных неограниченных результатов, полной пересортировки Q, таблицы пар всех ботов со всеми предметами и опроса всего мира в Tick. QA связывает эти решения с PERF-001–008. Превышение возвращается автору с конкретным trace/нагрузкой; уменьшение числа тестовых ботов ради красивого отчёта не считается исправлением. После проверки численные цели становятся версионированными принятыми бюджетами или меняются отдельным решением владельца с объяснением последствий.
