# Работа в проекте

Сначала прочитать [PROJECT.md](PROJECT.md), [TASKS.md](TASKS.md), последнюю контрольную точку и актуальную карточку своей задачи. Исходный запрос: [first_prompt](first_prompt). Текущий этап — проектирование; не заявлять наличие готового мода.

Применять [AIRules по зафиксированному коммиту](https://github.com/JoKeRooo7/AIRules/tree/8b74e311fec80a24d956e736174c7ae9aeec4fb0): ROUTER, команда gamedev, planning, task planning, task gate; подключать только нужные роли/правила. Если инструкции недоступны, явно сообщить об этом, не выдавать соответствие за проверенное.

Документация на русском в `docs/architecture`, `docs/modules`, `docs/logic`, `docs/system`, `docs/testing`. README даёт короткое описание и ссылки. Историю карточек задач сохранять новыми полными редакциями. Одна исполнительная задача — один самостоятельный проверяемый результат. Оркестратор согласованно обновляет TASKS; профильные специалисты передают изменения с ID и доказательствами.

Каждая логическая часть выполняет свою обязанность: подготовка входа, расчёт, маршрутизация, оркестрация, изменение мира и отображение разделены. Условия последовательны, составные критерии названы. Не делать универсального агента со всеми ролями внутри одного метода. Для кода действует один возврат в конце функции, `assert` только в тестах; ограничения Unreal `check/ensure` разбирать отдельно по правилам C++ перед реализацией.

Не использовать внешние API в runtime. Не предполагать существование непроверенных игровых методов. Новые операции с миром выполняет authority; UI отправляет намерение, а не самостоятельно изменяет инвентарь. Любая асинхронная рекомендация привязана к версии снимка и повторно проверяется на границе изменения мира.

Нельзя обещать полностью ванильный мультиплеер до проверки подключения, загрузки классов и долгого игрового сценария. Не имитировать реальные сетевые аккаунты ботов. Незнакомые модовые объекты по умолчанию доступны только для чтения до проверки адаптера.

Каждый выбранный алгоритм имеет оценку времени/памяти, альтернативы и независимый review. Непроверенное в игре отмечается явно. Существенные расхождения требований и правил записать в реестр решений и предъявить владельцу; независимую работу продолжать.
